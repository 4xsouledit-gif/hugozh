## 这一页解决什么问题

Hugo 跑完之后，站点只是本机上的一堆文件（默认在项目根目录的 `public/` 下）。这一章解决的是**最后一公里**：怎样把这堆文件送到一台会回应 HTTP 请求的服务器或对象存储上，让别人能用浏览器打开。

「部署」听起来像一个动作，实际是四件事连在一起，任何一环填错都会表现为「打不开」：

1. **构建**：`hugo` 把 `content/` 渲染成 `public/`；
2. **搬运**：把 `public/` 的内容送到远端（命令同步，或平台的构建机自动执行）；
3. **寻址**：远端用哪个域名对外服务，以及站点配置里的 `baseURL` 是否与之一致；
4. **验证**：用一个能看见的结果确认文件真的在远端，而不是只看日志里的「成功」。

本章页面分两类，按你的场景选一类即可：**通用部署命令**（本机执行命令同步产物）与**托管平台集成**（把源码推到 Git 仓库，平台自动构建并发布）。

## 读完本章你应该能够

- 说清**构建**与**部署**的分工：`hugo` 只负责产出 `public/`，部署工具只负责搬运，两者互不代劳；
- 判断自己的场景该走命令行同步，还是托管平台的 Git 集成；
- 在平台上填对四个关键值：**构建命令**、**发布目录**、**Hugo 版本**、**站点地址（`baseURL`）**；
- 用一个能看见的结果确认站点真的上线了；
- 遇到失败时，按症状找到对应入口，而不是反复重跑部署。

1. **先读完本页的「部署前必须确认的四件事」**——它适用于所有平台，跳过这一步正是绝大多数「部署成功但打不开」的根因。

## 从本地 public/ 到线上可访问：三种路线

无论选哪条路线，产物、变量与验证点是同一套，区别只在「谁执行构建」：

| 路线 | 你在本机执行 | 远端执行 | 适合 |
| --- | --- | --- | --- |
| 命令行同步 | `hugo` + 部署命令（`hugo deploy`、`rclone sync`、`rsync`） | 只接收文件 | 已有服务器或对象存储；想控制每次发布的时机 |
| 平台 Git 集成 | `git push` | 平台装工具链、构建、发布 | 没有服务器；希望每次提交自动上线 |
| 平台 Git 集成 + CI 工作流 | `git push` | GitHub Actions、GitLab CI、Forgejo Actions 构建后交给 Pages | 需要自定义工具版本、图片处理或压缩 |

三条路线共用的关键值只有四个，任何平台页面都在教你填这四个：

| 关键值 | 常见取值 | 填错的表现 |
| --- | --- | --- |
| 构建命令 | `hugo` 或 `hugo build --gc --minify` | 平台报「构建脚本退出码 1」，或产物目录为空 |
| 发布目录 | `public` | 部署成功但站点 404，或首页是平台的空页 |
| Hugo 版本 | 与本地一致的版本号（例如 `0.167.0`） | 本地正常、线上报模板或参数不存在 |
| 站点地址 | 配置里的 `baseURL` | 页面能开，但 CSS、图片、站内链接指向错误地址 |

## 部署前必须确认的四件事

1. **站点能在本地正常构建和预览。** 在项目根目录执行 `hugo`，退出码应当是 0；构建结束打开 `public/index.html`，应当能看到你的首页内容。这一步没过就不要动部署工具——部署工具不会替你修构建错误。参见[快速开始](/getting-started/quick-start/)与[基本用法](/getting-started/basic-usage/)。
2. **清楚构建命令与发布目录。** 构建命令通常是 `hugo`（新版本也接受 `hugo build`），发布目录默认是项目根目录下的 `public`，其位置由[配置](/configuration/)中的 `publishDir` 决定。把你的实际值记下来，后面每个平台都要填这两项。
3. **站点根地址已经设置正确。** 页面里的绝对链接、站点地图（sitemap）和 RSS 都依赖 `baseURL`；如果打算绑定自定义域名，最好在部署前就把它改成最终地址，免得上线后再改一遍。判断方法：构建后搜索 `public/index.html`，里面出现的绝对地址应当是你期望的域名。
4. **知道构建产物会出现在哪里。** 托管平台的「输出目录」「artifacts」「publish directory」一类设置，指的就是这个目录。填了源码目录（`content/`、仓库根目录）而不是发布目录，是新手最常见的 404 来源。

## 常见坑（跨平台通用）

| 症状 | 真因 | 怎么修 |
| --- | --- | --- |
| 平台日志显示部署成功，打开网址却是 404 或平台默认页 | 发布目录填成了仓库根目录或 `content/` | 改成 `public`；平台页面里的「发布目录」一节写了该平台的具体叫法 |
| 页面能打开，但样式、图片全丢，链接指向奇怪的域名 | `baseURL` 还是本地地址或临时域名 | 把 `baseURL` 改成最终访问地址后重新部署；用[域名与重定向注意事项](#域名与重定向注意事项)逐条核对 |
| 本地构建正常，平台报模板或参数不存在 | 平台的 Hugo 版本比本地旧 | 在平台配置里显式指定 `HUGO_VERSION`，与本地 `hugo version` 的输出保持一致 |
| 平台构建报 `command not found: hugo` | 平台镜像里没有 Hugo，或版本声明写在平台读不到的位置 | 按对应平台页把版本变量写进配置文件（`netlify.toml`、`amplify.yml`、工作流 `env` 等） |
| 部署成功，但几分钟内看到的还是旧页面 | CDN 或浏览器缓存 | 强制刷新；确认平台的缓存与失效设置，见本页「缓存」一条 |
| 站点在子路径（例如 `https://user.github.io/repo/`）下链接全错 | `baseURL` 少了子路径，或模板里硬编码了以 `/` 开头的绝对地址 | 让平台把完整地址传给构建（GitHub Pages 的 `--baseURL`、GitLab 的 `CI_PAGES_URL` 都是这个用途） |

分诊与更系统的排查方法见[故障排查](/troubleshooting/)；部署前想先自查一遍站点，可以跑[审计](/troubleshooting/audit/)。

## 关于构建产物

Hugo 每次构建都会重新生成发布目录，因此：

> [!WARNING]
> 不要把发布目录（`public`）的内容提交到 Git 仓库。Hugo 会在下次构建时重新创建它。正确做法是在 `.gitignore` 中忽略它，只提交源码与配置文件。

托管平台只需要「源码加构建命令」，不需要你提交构建结果；把产物一起提交反而容易让仓库里留下过期文件，掩盖真正的构建问题。

## 域名与重定向注意事项

- **自定义域名**：临时域名只在测试阶段有意义。绑定自定义域名后，记得把 `baseURL`（或平台传给构建的等价变量）改成该域名并重新部署，否则页面内的绝对链接仍指向临时地址。
- **404 页面**：静态托管平台一般提供自定义 404 的入口。在 `layouts/` 中定义 404 模板，构建后会得到 `public/404.html`，再在平台侧把它设为错误页。
- **重定向与尾斜杠**：Hugo 默认输出以 `/` 结尾的 URL。如果平台强制去除尾斜杠或做大小写归一化，可能出现重定向循环或 404。上线后建议抽查几个页面。
- **缓存**：静态资源的缓存策略由平台控制，重新部署不等于所有访客立刻拿到新文件。更新样式或图片后要留意旧缓存的影响。
