## 这一页解决什么问题

你不需要「更多工具」，你需要**判断哪一个工具值得装**。这一章收集的都是 Hugo 之外的第三方项目：它们要么替你少打些字，要么替你提供一个图形界面，要么给静态站点补上搜索或迁移能力。

这一页先给你一张选型地图和一条验证路径；每一类工具的细节在各自的子页面里，并都给出了**最小可用步骤**与**你应当看到什么**。

## 读完本章你应该能够

- 面对「编辑器插件、可视化 CMS、站内搜索、迁移工具」四类需求，不看广告词就知道该翻哪一页；
- 对候选工具跑一次最小验证（装插件看高亮 / 连仓库看提交 / 建索引看请求 / 导一篇文章看 front matter），在半小时内做出取舍；
- 分辨工具**读写的到底是什么**：Markdown 内容、前置元数据（front matter）、`hugo.toml` 配置，还是构建产物；
- 在工具不再维护、或它改坏了内容文件时，用一条 `git diff` 与一次 `hugo` 构建回到已知可用状态。

## 建议阅读顺序

按你眼下的问题选一条路，不必通读：

| 你的处境 | 从哪开始 | 为什么 |
| --- | --- | --- |
| 已经在用某个编辑器，只是觉得写 Hugo 模板没高亮、没补全 | [编辑器](/tools/editors/) | 改动最小：装一个插件，工作流不变 |
| 团队里有人不写 Markdown，需要一个网页后台改文章 | [前端框架与构建工具](/tools/front-ends/) | 这类工具直接读写 Git 仓库，不改变构建方式 |
| 访客找不到内容，想要站内搜索 | [站内搜索](/tools/search/) | 先弄清「构建期索引」与「第三方服务」的分界 |
| 内容在 Jekyll / WordPress / Medium 等旧系统里 | [从其他系统迁移](/tools/migrations/) | 先迁移再谈其他工具，否则边搬边改会返工 |
| 都不属于以上几类（图库、分析、嵌入等） | [其他工具](/tools/other/) | 周边项目清单 |

三部曲式的稳妥顺序是：**先迁移（内容到位）→ 再选编辑器或 CMS（内容好写）→ 最后加搜索（内容好找）**。反过来做也能成，但迁移会推翻前面配好的站点参数与固定链接。

## 本节概览

Hugo 本身只做一件事：把内容与模板编译成静态站点。围绕这项工作，社区与商业公司开发了大量第三方工具，覆盖编写内容、编辑可视化界面、站内搜索，以及从其他系统迁移这几类需求。本节按用途把它们分门别类地列出来，方便你按需挑选。

这些工具都由 Hugo 之外的团队独立开发与维护，Hugo 项目不对它们的可用性、安全性或后续维护作出保证。选用之前，建议先确认它是否仍在更新、是否支持你当前使用的 Hugo 版本。

## 如何选择

如果只是想少打几个字，先看[编辑器](/tools/editors/)：这类插件装进你已经在用的编辑器即可，改动最小。若你或团队的编辑者不习惯直接写 Markdown，[前端框架与构建工具](/tools/front-ends/)里的可视化 CMS 更合适，它们通常直接读写 Git 仓库中的内容文件，与 Hugo 的构建流程互不干扰。给站点加搜索要从[站内搜索](/tools/search/)入手：内容规模不大时，用构建期生成的 JSON 索引配合客户端脚本就够了；体量很大或需要多语言分词时，再考虑第三方搜索服务。

至于从旧系统搬到 Hugo，先看[从其他系统迁移](/tools/migrations/)。Jekyll 用户可以直接用 Hugo 内置的 [hugo import jekyll](/commands/hugo-import-jekyll/) 命令，无需额外安装工具；其他系统则多半要先导出成 Markdown 或 XML，再交给社区工具转换。迁移过程涉及内容目录的组织方式，建议同时对照[目录结构](/getting-started/directory-structure/)与[内容管理](/content-management/)两节，把源站点的分类、标签与固定链接映射到 Hugo 的概念上，避免搬运完成后还要返工。

## 引入任何第三方工具之后，这三个事实不变

选型时容易被忽略的是：第三方工具都在**外围**工作，Hugo 的核心流程不会因此改变。记住这三条，你就能随时退回来：

| 不变的事实 | 意味着什么 | 怎么自证 |
| --- | --- | --- |
| 内容仍然是 `content/` 下的普通 Markdown 文件 | CMS 只是换了一种编辑这些文件的方式，不接管渲染 | `git diff --stat` 里应只有 `content/` 下的 `.md` 变化 |
| 构建仍然是 `hugo` | 工具可以触发构建，但结果由 Hugo 决定 | 关掉工具后执行 `hugo --renderToMemory`，退出码仍应为 0 |
| 站点仍是纯静态产物 | 搜索若不依赖服务器，索引就只是 `public/` 里的一个文件 | 构建后检查 `public/` 中是否多出索引文件 |

只要这三条成立，卸载工具就是「删掉插件、删掉配置文件」，站点不会因此报废。

## 选型时的自检清单

在把一个工具接入生产站点之前，逐条打勾：

1. **许可证与维护状态**：仓库最近一次提交是什么时候？有没有对得上你 Hugo 版本的说明？
2. **它写哪些文件**：只读内容？还是也会改 `hugo.toml`、`layouts/`？（会写模板的工具要格外小心）
3. **出错时能不能看见**：改坏的差异是否落在 Git 里、能否 `git checkout` 回退？
4. **能否离线**：只依赖 Hugo 的功能（如构建期索引）在断网与内网环境里同样可用。
5. **退出成本**：卸载它之后，站点是否仍能用纯 `hugo` 构建？——上文三条就是判据。

## 常见坑

| 症状 | 真因 | 怎么修 |
| --- | --- | --- |
| 装了工具，`hugo` 却报文件解析错误 | 工具按自己的格式写了前置元数据（例如留了不存在的键、破坏了 `+++` 与 `---` 的配对） | 用 `git diff` 找出被改的页面，对照[前置元数据](/content-management/front-matter/)修正；把工具的输出限制在 `content/` 内 |
| 工具界面里能看到文章，站点上却没有 | 工具改的不是 Hugo 实际读取的那份文件（写到了别的分支/目录，或文件名大小写不一致） | 在项目根目录执行 `hugo list all`，看该文章是否出现在清单里 |
| 搜索结果为空 | 索引文件没有被构建出来，或前端请求的路径不对 | 构建后确认 `public/` 下存在索引文件，再打开浏览器开发者工具的 Network 面板看请求返回什么 |
| 迁移后大量链接 404 | 源站固定链接没有映射成 Hugo 的目录结构 | 见[从其他系统迁移](/tools/migrations/)的验证一节，并配置 `aliases` 或重定向 |
| 报错看不懂 | 报错来自工具而不是 Hugo | 先执行 `hugo --renderToMemory`：退出码 0 说明问题在工具侧，退出码非 0 才是 Hugo 侧的问题 |

更多排查入口见[故障排查](/troubleshooting/)。
